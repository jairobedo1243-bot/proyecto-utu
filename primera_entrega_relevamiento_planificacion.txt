PRIMERA ENTREGA - RELEVAMIENTO Y PLANIFICACION INICIAL
======================================================

Proyecto: SGRSI - Sistema de Gestion de Recursos y Soporte de Informatica


1. RELEVAMIENTO DE DATOS
========================

Objetivo del relevamiento:
Conocer como se administran actualmente los recursos informaticos, los prestamos de equipos,
las incidencias tecnicas y las solicitudes de servicio dentro de la institucion.

Tecnicas utilizadas:

- Entrevista a usuarios administrativos y docentes.
- Observacion del proceso actual de soporte.
- Analisis de formularios o registros existentes.
- Cuestionario breve para usuarios finales.

Datos a relevar:

- Tipos de usuarios que utilizaran el sistema.
- Equipos informaticos disponibles.
- Ubicacion de equipos.
- Estados posibles de los equipos.
- Tipos de incidencias tecnicas.
- Proceso de prestamo y devolucion.
- Solicitudes frecuentes de servicio.
- Reportes necesarios para la administracion.


2. FORMULARIOS DE RECOLECCION DE INFORMACION
============================================

Formulario para solicitudes de servicio:

- Descripcion.


3. ESTUDIO DE FACTIBILIDAD
==========================

Factibilidad tecnica:
El sistema es tecnicamente viable porque utiliza tecnologias conocidas y disponibles:
HTML5, CSS3, JavaScript, Bootstrap y MySQL/MariaDB para el diseno de persistencia.
Puede ejecutarse inicialmente como prototipo web en equipos de laboratorio.

Factibilidad operativa:
El sistema es operativo porque responde a necesidades reales de administracion:
control de inventario, registro de tickets, prestamos y solicitudes.
Los usuarios principales son administrativos, tecnicos y solicitantes.

Factibilidad economica:
Es viable economicamente porque se apoya en herramientas gratuitas o de codigo abierto.
No requiere licencias pagas para la primera etapa del proyecto.

Factibilidad legal:
El sistema debe respetar buenas practicas de seguridad y privacidad.
Los datos personales de usuarios deben usarse solo para fines institucionales.

Conclusion:
El proyecto es factible para una primera version academica, con posibilidad de evolucionar
hacia una aplicacion completa conectada a base de datos.

5. ESPECIFICACION DE REQUERIMIENTOS - IEEE 830
==============================================

5.1 Proposito
-------------
Definir los requerimientos del SGRSI para controlar recursos informaticos,
prestamos, tickets de soporte y solicitudes de servicio.

5.2 Alcance
-----------
El sistema permitira:

- Iniciar sesion con roles de prueba.
- Navegar por modulos.
- Registrar equipos en inventario desde el prototipo.
- Registrar tickets.
- Registrar prestamos.
- Registrar solicitudes.
- Visualizar dashboard basico.
- Aplicar validaciones del lado del cliente.

Limitaciones:

- En primera entrega, el guardado es principalmente prototipo en interfaz.
- No se implementa backend productivo obligatorio.
- La base de datos se entrega como modelo de persistencia mediante SQL y DER.

5.3 Usuarios del sistema
------------------------

Administrador:
Gestiona usuarios, inventario, reportes y supervision general.

Tecnico:
Atiende tickets, controla prestamos, consulta inventario y registra tareas.

Solicitante:
Registra incidencias y solicitudes de servicio.

5.4 Requerimientos funcionales
------------------------------

RF01 - El sistema debe permitir iniciar sesion con usuarios de prueba.
RF02 - El sistema debe mostrar modulos segun el rol del usuario.
RF03 - El sistema debe permitir registrar equipos desde un formulario.
RF04 - El sistema debe validar campos obligatorios.
RF05 - El sistema debe permitir crear tickets de soporte.
RF06 - El sistema debe permitir registrar prestamos.
RF07 - El sistema debe permitir registrar solicitudes de servicio.
RF08 - El sistema debe mostrar mensajes de exito o error.
RF09 - El sistema debe permitir cerrar sesion.
RF10 - El sistema debe contar con una estructura de base de datos documentada.

5.5 Requerimientos no funcionales
---------------------------------

RNF01 - La interfaz debe ser responsive para celulares y tablets.
RNF02 - El sitio debe utilizar HTML5 semantico.
RNF03 - Los estilos deben estar separados en archivos CSS.
RNF04 - El comportamiento debe estar separado en JavaScript.
RNF05 - El sistema debe tener navegabilidad clara entre modulos.
RNF06 - El sistema debe usar un framework CSS justificado.
RNF07 - El codigo debe mantener nombres claros y consistentes.
RNF08 - La documentacion debe explicar el alcance de la primera entrega.

7. MODELO DE DESARROLLO
=======================

Modelo seleccionado: Tradicional en cascada.

Justificacion:
Para la primera entrega conviene usar un modelo tradicional porque el curso solicita
relevamiento, analisis, planificacion, diseno y documentacion antes de avanzar a una
implementacion completa. Este modelo permite ordenar las etapas y controlar entregables.

Etapas:

1. Relevamiento.
2. Analisis de requerimientos.
3. Diseno de interfaz y base de datos.
4. Implementacion HTML/CSS/JS.
5. Pruebas de formularios y navegabilidad.
6. Documentacion y entrega.

12. CPM / PERT RESUMIDO
=======================

Actividades y dependencias:

A - Relevamiento inicial.
B - Analisis de factibilidad. Depende de A.
C - Requerimientos. Depende de A.
D - Diseno MER. Depende de C.
E - Maquetacion HTML. Depende de C.
F - Estilos CSS. Depende de E.
G - JavaScript y validaciones. Depende de E.
H - Documentacion final. Depende de B, C, D, F y G.
I - Revision de entrega. Depende de H.

Camino critico estimado:
A -> C -> E -> F/G -> H -> I

Conclusion:
El mayor riesgo de retraso esta en requerimientos, interfaz y validaciones.
Por eso esas tareas deben controlarse semanalmente.
